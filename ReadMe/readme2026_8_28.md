## 1. 这两部分到底在解决什么问题

在简单的 `epoll` 服务器中，我们通常先关注：

1. 如何接收连接；
2. 如何读取数据；
3. 如何发送数据；
4. 如何关闭 socket。

但服务器开始使用 `Channel`、`EventLoop`、`Epoller`、`TcpConnection` 等对象之后，真正困难的问题变成了：

> 一个连接在什么时候创建、什么时候进入 epoll、什么时候修改监听事件、什么时候停止处理业务，以及什么时候销毁才安全？

如果生命周期没有设计好，程序即使在简单测试中能运行，也可能存在：

- 对未注册的 fd 执行 `MOD`；
- 对已经注册的 fd 再次执行 `ADD`；
- 内核 epoll 状态和用户态对象状态不一致；
- 一个关闭事件触发多次删除；
- 回调还没结束，对象就被 `delete`；
- `Epoller` 中留下指向已销毁 `Channel` 的悬空指针；
- 对已释放对象继续访问，产生 use-after-free；
- fd 被关闭两次，或根本没有关闭。

因此，这两个部分的核心不是“再增加几个函数”，而是建立两套清晰的状态和一条安全的资源释放路径：

```text
Channel 生命周期：
NEW → ADDED → DELETED

TcpConnection 生命周期：
CONNECTED → CLOSING → 销毁
```

第一套回答：

> Channel 当前和 epoll 是什么关系？

第二套回答：

> TcpConnection 当前是否还允许继续处理业务？

## 3. 前置知识

### 3.1 文件描述符 fd

Linux 用一个整数表示打开的资源。socket 创建成功后也会得到一个 fd。

```text
fd = 5
```

它只是一个编号，不是连接对象本身。操作系统将这个编号映射到内核中的 socket 资源。

### 3.2 非阻塞 I/O

非阻塞 socket 调用 `recv` 或 `send` 时，如果当前暂时不能继续处理，不会一直等待，而是返回 `-1`，并设置：

```text
errno = EAGAIN 或 EWOULDBLOCK
```

这通常表示：

> 连接仍然正常，只是现在没有更多数据可读，或者发送缓冲区暂时没有空间。

因此它是“稍后再试”，不是“连接已坏”。

### 3.3 epoll 的三个基本操作

`epoll_ctl` 主要有三种操作：

| 操作 | 含义 |
|---|---|
| `EPOLL_CTL_ADD` | 第一次把 fd 加入 epoll |
| `EPOLL_CTL_MOD` | 修改已在 epoll 中的 fd 所关注的事件 |
| `EPOLL_CTL_DEL` | 把 fd 从 epoll 中移除 |

调用哪一个操作，依赖 fd 当前是否已经在 epoll 中。这正是 `ChannelState` 存在的原因。

### 3.4 回调

`Channel` 不直接编写具体业务，而是保存回调：

```text
发生可读事件 → read callback
发生可写事件 → write callback
发生关闭事件 → close callback
```

通常使用 lambda 捕获 `this`，再用 `std::function` 保存：

```cpp
channel_.SetReadCallback([this] {
    ReadHandler();
});
```

需要特别区分：

- `Set...Callback` 或项目里的 `...Call()`：绑定函数；
- `...Handler()`：事件发生后真正处理。

绑定通常在构造或初始化阶段做一次，事件发生时不能把“重新绑定”误当成“执行处理”。

### 3.5 对象所有权与悬空指针

如果 A 创建并负责销毁 B，可以说 A 拥有 B。

如果某处只保存了 `B*`，但不负责销毁 B，它通常只是观察 B。B 销毁后，这个指针必须被移除，否则会成为悬空指针。

use-after-free 指的是：

> 对象已经释放，程序仍然通过旧指针或旧迭代器访问它。

这是未定义行为，可能崩溃，也可能暂时“看起来正常”。

## 4. 先认识项目中的核心对象

### 4.1 类职责关系

```text
TcpServer
├── 管理全部 TcpConnection
├── 接收连接关闭通知
└── 安排待销毁连接

TcpConnection
├── 拥有 socket fd
├── 拥有 Channel
├── 拥有输入/输出缓冲区
├── 处理读写业务
└── 发现自己需要关闭，但不销毁自己

Channel
├── 记录 fd
├── 记录想监听的事件 events_
├── 记录实际发生的事件 revents_
├── 记录自己与 epoll 的关系 state_
└── 保存并触发事件回调

EventLoop
├── 等待事件
├── 分发事件
├── 协调 Channel 更新
└── 在安全时间点执行清理

Epoller
├── 执行 epoll_wait / epoll_ctl
├── 同步用户态 Channel 与内核 epoll 状态
└── 记录 Channel*，但不拥有 Channel
```

### 4.2 所有权关系

```text
TcpServer owns TcpConnection
TcpConnection owns Channel 和 fd
Epoller observes Channel*
EventLoop 临时持有 active Channel* 列表
```

最重要的推论是：

> 销毁 `TcpConnection` 之前，必须先让其内部 `Channel` 脱离 `Epoller`。

否则 `TcpConnection` 析构后，内部 `Channel` 也消失，而 `Epoller` 或当前活跃事件集合中仍可能保存 `Channel*`。

## 5. 第一部分：Channel 生命周期管理

### 5.1 为什么 `events_` 不够用

`events_` 表示 Channel 希望内核监听哪些事件，例如：

```text
EPOLLIN
EPOLLIN | EPOLLOUT
```

但它不能回答：

> 这个 fd 当前是否已经注册到 epoll？

例如，下面两种 Channel 的 `events_` 都可能是 `EPOLLIN`：

```text
Channel A：刚创建，还没有进入 epoll
Channel B：已经在 epoll 中监听读事件
```

对 A 应执行 `ADD`，对 B 的事件修改应执行 `MOD`。因此还需要独立的生命周期状态。

### 5.2 ChannelState 三态

建议使用强类型枚举表达有限且互斥的状态：

```cpp
enum class ChannelState {
    New,
    Added,
    Deleted
};
```

#### New

对象已经创建，但从未成功加入 epoll。

```text
Channel 已存在
内核 epoll 中没有这个 fd
```

#### Added

`EPOLL_CTL_ADD` 已成功，fd 当前存在于 epoll 监听集合中。

监听事件发生变化时执行 `MOD`，状态仍然是 `Added`。

#### Deleted

Channel 曾经加入过 epoll，后来已成功移除。

它和 `New` 都表示“当前不在 epoll 中”，但语义不同：

- `New`：从未加入；
- `Deleted`：加入过，后来删除。

如果设计允许重新注册，可以存在：

```text
Deleted → Added
```

如果连接删除后立即销毁，那么 `Deleted` 主要用于明确删除已经完成和辅助排错。

### 5.3 Channel 状态机

```text
                  ADD 成功
          New ----------------> Added
                                 │  ▲
                                 │  │
                       MOD 成功  └──┘
                                 │
                                 │ DEL 成功
                                 ▼
                              Deleted
                                 │
                                 │ ADD 成功（仅当允许重新注册）
                                 └──────────────> Added
```

状态与操作的基本关系：

| 当前状态 | 请求 | 合理动作 | 成功后的状态 |
|---|---|---|---|
| `New` | 开始监听 | `ADD` | `Added` |
| `Added` | 修改监听内容 | `MOD` | `Added` |
| `Added` | 移除监听 | `DEL` | `Deleted` |
| `Deleted` | 重新监听（若允许） | `ADD` | `Added` |
| `New` | 移除 | 通常无需操作 | `New` |
| `Deleted` | 再次移除 | 幂等返回或报告无操作 | `Deleted` |

### 5.4 为什么枚举比多个 bool 更合适

如果使用：

```text
is_new
is_added
is_deleted
```

就可能出现矛盾组合：

```text
is_added = true
is_deleted = true
```

枚举使 Channel 在任意时刻只能处于一个状态，更适合表达有限状态机。

### 5.5 `events_`、`revents_`、`state_` 的区别

| 成员 | 回答的问题 | 示例 |
|---|---|---|
| `events_` | 我希望内核监听什么？ | `EPOLLIN | EPOLLOUT` |
| `revents_` | 内核这次告诉我发生了什么？ | `EPOLLIN | EPOLLHUP` |
| `state_` | 我当前和 epoll 是什么关系？ | `Added` |

不要用 `events_ == 0` 推断 Channel 不存在或不在 epoll 中。一个对象可以仍处于 `Added`，但暂时不关注普通读写事件。

### 5.6 状态改变必须发生在系统调用成功之后

错误思路：

```text
先把 state 改成 Added
再调用 epoll_ctl(ADD)
```

如果 `ADD` 失败：

```text
内核：没有这个 fd
Channel：认为自己是 Added
用户态映射：可能已经保存 Channel*
```

三份状态发生冲突。

正确原则：

```text
检查旧状态
↓
尝试 epoll_ctl
↓
确认成功
↓
更新容器和 Channel 状态
```

`DEL` 同理：只有内核删除成功后，才从映射中移除并设置 `Deleted`。

### 5.7 Channel 更新的设计思路

Channel 修改 `events_` 后不直接操作 epoll，而是发出更新通知：

```text
Channel::EnableWrite
↓
修改 events_
↓
Channel::Update
↓
update callback
↓
EventLoop::UpdateChannel
↓
Epoller 根据 ChannelState 决定 ADD 或 MOD
```

这样划分的好处：

- `Channel` 只描述自身状态和事件；
- `EventLoop` 负责协调；
- `Epoller` 集中处理所有内核接口和同步规则；
- 业务对象不需要知道 `epoll_ctl` 的细节。

### 5.8 第一部分的四个典型流程

#### 新连接加入

```text
accept 得到 clientfd
↓
创建 TcpConnection
↓
内部创建 Channel，状态 New
↓
设置希望监听 EPOLLIN
↓
通知 EventLoop / Epoller
↓
Epoller 判断为 New，执行 ADD
↓
ADD 成功，状态变 Added
```

#### 有响应数据，需要关注可写

```text
业务产生 output buffer
↓
Channel::EnableWrite
↓
events_: EPOLLIN → EPOLLIN | EPOLLOUT
↓
状态仍是 Added
↓
Epoller 执行 MOD
```

#### 发送完成，取消关注可写

```text
output buffer 发送完成
↓
Channel::DisableWrite
↓
events_: EPOLLIN | EPOLLOUT → EPOLLIN
↓
状态仍是 Added
↓
Epoller 执行 MOD
```

#### 连接退出

```text
连接被判定需要关闭
↓
安全清理阶段调用 RemoveChannel
↓
当前状态 Added
↓
Epoller 执行 DEL
↓
成功后从映射移除
↓
状态变 Deleted
```

## 6. 第二部分：TcpConnection 生命周期管理

### 6.1 为什么还要有 ConnectionState

`ChannelState` 管理的是 Channel 与 epoll 的关系，它不能表示连接是否还允许处理业务。

一次 epoll 事件可能同时包含多个标志：

```text
EPOLLIN | EPOLLHUP
```

或者 `ReadHandler` 已经发现对端关闭，随后 `HandlerEvent` 又继续检查 `EPOLLHUP`。如果没有连接状态，同一连接可能重复触发关闭，甚至在已决定关闭后继续写业务数据。

因此需要独立的连接状态：

```cpp
enum class ConnectionState {
    Connected,
    Closing,
    Closed
};
```

### 6.2 ConnectionState 状态机

```text
              发现正常关闭 / 致命错误 / HUP / ERR
Connected ----------------------------------------> Closing
                                                       │
                                                       │ 延迟清理
                                                       ▼
                                                    对象销毁
```

`Closed` 可以保留给更复杂的设计，但在当前原始指针版本中，对象一旦真正销毁，就没有人能安全读取它的 `Closed` 状态。因此当前实际流程可以简化为：

```text
Connected → Closing → 销毁
```

### 6.3 状态必须在构造时初始化

对象构造完成后应该处于确定、合法、可用的状态。

不要依赖 `TcpServer` 在 `new TcpConnection` 后再补一次 `SetState(Connected)`。更稳妥的思想是：

```cpp
TcpConnection(int fd)
    : fd_(fd),
      state_(ConnectionState::Connected),
      channel_(fd) {}
```

否则，在服务器设置状态之前，任何读取 `state_` 的行为都可能访问未初始化值。

### 6.4 哪些情况应该关闭

#### 正常关闭

`recv` 返回 `0` 表示对端已经关闭其发送方向。对于当前简单服务器，可以把它视为连接结束并进入关闭流程。

#### 致命读写错误

`recv` 或 `send` 返回 `-1`，且错误不是可恢复情况时，应记录错误并进入关闭流程。

#### epoll 异常事件

`EPOLLHUP` 和 `EPOLLERR` 通常也应汇入统一关闭入口。

注意：它们通常不需要像 `EPOLLIN / EPOLLOUT` 一样主动“订阅”。内核会在发生时报告。

#### 不能关闭的情况：EAGAIN / EWOULDBLOCK

```text
EAGAIN
→ 当前操作暂时无法继续
→ 返回事件循环
→ 等下一次通知
→ 不关闭连接
```

此外，稳健代码通常还会单独考虑 `EINTR`：系统调用被信号中断时可以重试，而不是直接判定为致命错误。

### 6.5 统一关闭入口

关闭原因很多，但资源释放路径应该只有一条：

```text
recv == 0 ────────────┐
recv 致命错误 ────────┤
send 致命错误 ────────┤
EPOLLHUP ──────────────┤
EPOLLERR ──────────────┘
                       ↓
              TcpConnection::HandleClose
                       ↓
          Connected → Closing（只允许一次）
                       ↓
              通知 TcpServer 待关闭
```

这样可以避免每个错误分支都各写一套：

```text
RemoveChannel
close(fd)
erase map
delete connection
```

如果释放逻辑散落在多个分支中，非常容易少做、重复做或顺序不一致。

### 6.6 关闭入口为什么要幂等

幂等可以简单理解为：重复请求不会重复产生副作用。

```cpp
void HandleClose() {
    if (state_ != ConnectionState::Connected) {
        return;
    }

    state_ = ConnectionState::Closing;
    TriggerClose(fd_);
}
```

第一次调用：

```text
Connected → Closing → 通知服务器
```

后续再次调用：

```text
已经 Closing → 直接返回
```

这可以处理 `EPOLLIN | EPOLLHUP`、读回调与关闭回调重复发现问题等情况。待删除集合去重仍可以作为第二层保险。

### 6.7 TcpConnection 为什么不能销毁自己

`TcpConnection` 最清楚自己的 I/O 是否已经失败，所以它适合：

> 发现自己应该退出。

但它不知道外部还有哪些位置保存了自己的地址：

```text
TcpServer::connections_ 保存 TcpConnection*
Epoller 保存内部 Channel*
EventLoop 当前 activeChannels 保存 Channel*
当前调用栈正在运行 Channel::HandlerEvent
```

因此它不适合 `delete this`，也不应在读写回调中直接让服务器立即删除自己。

正确职责是：

```text
TcpConnection：提出关闭请求
TcpServer：掌握并结束连接生命周期
```

### 6.8 为什么不能在回调中立即 delete

假设当前调用链是：

```text
EventLoop::Distribute
↓
Channel::HandlerEvent
↓
TcpConnection::ReadHandler
↓
发现关闭
↓
TcpServer::RemoveConnection
↓
delete TcpConnection
```

`Channel` 是 `TcpConnection` 的成员。删除 `TcpConnection` 会同时销毁 `Channel`。

但此时 `Channel::HandlerEvent()` 还没有返回。控制流回到它以后，仍可能继续检查 `EPOLLOUT`、`EPOLLHUP` 或 `EPOLLERR`。此时它的 `this` 已经无效，形成 use-after-free。

这类错误最危险的地方是：

- 不一定每次崩溃；
- 简单测试可能完全正常；
- 优化级别、并发量或内存布局变化后才暴露。

### 6.9 解决方法：逻辑关闭与物理销毁分离

#### 逻辑关闭

```text
连接已经不能继续使用
状态变为 Closing
通知服务器
加入待清理集合
```

对象此时仍然存在，只是不再处理新业务。

#### 物理销毁

```text
RemoveChannel
从连接表移除
销毁 TcpConnection
关闭 fd
```

物理销毁必须等当前事件回调链完全退出后执行。

### 6.10 延迟销毁

事件循环从：

```text
Poll → Distribute → 下一轮 Poll
```

升级为：

```text
Poll
↓
Distribute 本轮全部事件
↓
Cleanup 待删除连接
↓
下一轮 Poll
```

完整示例：

```text
epoll_wait 返回 Channel A、B、C
↓
A 正常处理
↓
B 发现连接关闭，只标记待删除
↓
B 的全部回调安全返回
↓
C 正常处理
↓
Distribute 完全结束
↓
Cleanup 真正删除 B
```

### 6.11 待删除集合的设计

服务器收到关闭通知后，先保存 fd 或连接标识，不立即删除。

选择容器时应保证重复关闭请求不会导致重复销毁：

- 使用集合天然去重；或
- 使用顺序容器，在加入或清理前去重；或
- 主要依靠 `ConnectionState::Closing` 阻止重复请求，容器再做防御性去重。

当前单线程 Reactor 中，以 fd 作为待删除标识可以工作，但必须警惕 fd 复用：旧连接关闭后，操作系统可能很快把相同数字分配给新连接。更成熟的设计会用连接对象身份、智能指针、唯一编号或“同一轮结束前立即清理”的严格约束降低风险。

### 6.12 安全清理顺序

在 Cleanup 阶段处理连接时，推荐顺序是：

```text
1. 在 connections_ 中找到目标连接
2. 让 Channel 脱离 epoll（EPOLL_CTL_DEL）
3. Epoller 移除保存的 Channel*
4. 从 connections_ 解除所有权
5. 销毁 TcpConnection
6. TcpConnection 析构时关闭 fd
```

对于原始指针容器，可用局部变量保存指针，避免迭代器失效后继续访问：

```cpp
auto* connection = it->second;

if (!poller.RemoveChannel(&connection->GetChannel())) {
    // 记录失败并按项目策略处理，不能假装清理成功
    return;
}

connections_.erase(it);
delete connection;
```

也可以先 `delete` 再 `erase`，只要删除后不再解引用指针且迭代器仍有效；但“先从所有者容器解除，再销毁局部保存的对象”通常更容易审查。若使用 `std::unique_ptr`，所有权会更清楚。

关键不在于两行代码的固定形式，而在于满足以下不变量：

- 删除对象前，Epoller 不再观察其 Channel；
- 容器和对象只清理一次；
- 删除后不再访问对象或失效迭代器；
- fd 只由明确的唯一所有者关闭。

## 7. 两部分合起来的完整流程

### 7.1 连接创建

```text
Acceptor 接收 clientfd
↓
TcpServer 创建 TcpConnection
↓
TcpConnection 构造时：
  state = Connected
  创建内部 Channel，Channel state = New
  绑定读、写、关闭回调
  设定关注 EPOLLIN
↓
TcpServer 保存 TcpConnection
↓
EventLoop 将 Channel 交给 Epoller
↓
Epoller 执行 ADD
↓
成功后 Channel state = Added
```

### 7.2 正常读写

```text
epoll_wait 返回可读事件
↓
Epoller 设置 Channel::revents_
↓
EventLoop 调用 Channel::HandlerEvent
↓
Channel 触发 ReadHandler
↓
循环 recv，直到 EAGAIN
↓
业务产生输出数据
↓
EnableWrite 修改 events_
↓
Epoller 对 Added Channel 执行 MOD
↓
发生可写事件，发送剩余数据
↓
发送完成后 DisableWrite
↓
再次 MOD，只保留需要关注的事件
```

### 7.3 客户端正常关闭

```text
recv 返回 0
↓
ReadHandler 调用统一 HandleClose
↓
ConnectionState: Connected → Closing
↓
通过 close callback 通知 TcpServer
↓
TcpServer 将目标加入待清理集合
↓
当前 HandlerEvent 返回
↓
本轮 Distribute 完成
↓
Cleanup
↓
Epoller DEL Channel
↓
ChannelState: Added → Deleted
↓
从 connections_ 移除
↓
销毁 TcpConnection
↓
析构关闭 fd
```

### 7.4 致命错误或 HUP/ERR

```text
记录不同的错误原因
↓
全部进入同一个 HandleClose
↓
后续流程与正常关闭完全相同
```

这就是“原因可以不同，释放路径只有一条”。

### 7.5 必须一直成立的不变量

不变量是系统在任何合法时刻都应满足的规则：

1. `ChannelState::Added` 表示内核 epoll 和用户态映射都记录了它。
2. `New` 或 `Deleted` 的 Channel 不应被当作活跃 Channel 分发。
3. `Epoller` 保存 `Channel*` 时，对应 `TcpConnection` 必须仍然存活。
4. `ConnectionState::Closing` 的连接不得继续产生新业务操作。
5. 一个关闭请求最多安排一次物理销毁。
6. 物理销毁不发生在对象自己的事件回调栈中。
7. 销毁连接前，Channel 已从 Epoller 中移除。
8. fd 只有一个明确的关闭责任人。

## 8. 关键代码思维

本节只展示表达设计的最小骨架，不粘贴完整源码。

### 8.1 用类型区分不同概念

不要让 `ReadResult::Close` 和 `ConnectionState::Closed` 共享容易混淆的裸枚举名。优先使用 `enum class`：

```cpp
enum class IoResult { Data, Again, PeerClosed, FatalError };
enum class ConnectionState { Connected, Closing, Closed };
enum class ChannelState { New, Added, Deleted };
```

这样调用时必须写：

```cpp
state_ = ConnectionState::Closing;
```

而不能误写成另一个枚举中的 `Close`。

### 8.2 回调只绑定一次

```cpp
void BindCallbacks() {
    channel_.SetReadCallback([this] { ReadHandler(); });
    channel_.SetWriteCallback([this] { WriteHandler(); });
    channel_.SetCloseCallback([this] { HandleClose(); });
}
```

事件发生时调用 `HandleClose()`，不是再次调用 `BindCallbacks()`。

### 8.3 统一关闭入口

```cpp
void HandleClose() {
    if (state_ != ConnectionState::Connected) {
        return;
    }
    state_ = ConnectionState::Closing;
    if (closeCallback_) {
        closeCallback_(fd_);
    }
}
```

它只做三件事：

1. 防止重复关闭；
2. 切换到逻辑关闭状态；
3. 通知真正的生命周期管理者。

### 8.4 I/O 结果只负责描述结果

```text
Data       → 继续处理数据
Again      → 返回事件循环，不关闭
PeerClosed → HandleClose
FatalError → 记录错误后 HandleClose
```

让 `Read()` / `Write()` 返回结果，让 Handler 决定控制流，可以减少底层函数中散落的资源管理代码。

### 8.5 Epoller 按状态选择操作

伪代码：

```text
UpdateChannel(channel):
    if state == New:
        尝试 ADD
        成功后记录指针并设为 Added

    else if state == Added:
        尝试 MOD
        成功后保持 Added

    else if state == Deleted 且允许重新加入:
        尝试 ADD
        成功后记录指针并设为 Added
```

### 8.6 EventLoop 提供安全清理点

```text
while running:
    activeChannels = Poll()
    for channel in activeChannels:
        channel.HandleEvent()
    Cleanup()
```

`Cleanup()` 放在整轮分发之后，而不是某个 Handler 的内部。

### 8.7 回调都要判空

`std::function` 未绑定时直接调用会抛出 `std::bad_function_call`。读、写、关闭回调应遵循一致的判空策略。

## 9. 常见错误、原因与解决方法

### 错误 1：用 `events_` 代替 Channel 生命周期状态

**表现**：根据是否包含 `EPOLLIN` 或是否为 0 判断该执行 `ADD` 还是 `MOD`。

**原因**：监听内容和注册状态是两个维度。

**解决**：使用独立的 `ChannelState`。

### 错误 2：对 New Channel 执行 MOD

**表现**：`epoll_ctl(EPOLL_CTL_MOD)` 返回错误。

**原因**：fd 从未加入 epoll。

**解决**：`New → ADD`，只有 `Added → MOD`。

### 错误 3：先改状态，再调用 epoll_ctl

**表现**：系统调用失败后，Channel 却显示 `Added` 或 `Deleted`。

**原因**：把“准备执行”误当成“执行成功”。

**解决**：系统调用成功后再提交状态变化和容器变化。

### 错误 4：认为 Epoller 拥有 Channel

**表现**：Epoller 删除 Channel，或连接销毁后映射中还留着 `Channel*`。

**原因**：没有区分记录指针与对象所有权。

**解决**：明确 `TcpConnection owns Channel`，`Epoller observes Channel*`；销毁前先解除观察关系。

### 错误 5：Channel 析构时关闭 fd

**表现**：`TcpConnection` 也关闭 fd，形成重复关闭；复用后的新 fd 甚至可能被误关。

**原因**：fd 所有权不清晰。

**解决**：指定唯一所有者。当前设计中由 `TcpConnection` 析构关闭 fd，Channel 只记录 fd。

### 错误 6：发生 CLOSE 时再次调用 CloseCall

**表现**：连接没有关闭，只是重新绑定回调。

**原因**：混淆“注册回调”和“执行处理”。

**解决**：初始化时绑定一次；事件发生时调用 `HandleClose()`。

### 错误 7：ERROR 只清空缓冲区，不关闭连接

**表现**：坏连接仍在 epoll 中，被反复唤醒。

**原因**：清理业务数据不等于结束连接生命周期。

**解决**：致命错误记录原因后进入统一关闭入口。

### 错误 8：把 EAGAIN 当作致命错误

**表现**：正常的非阻塞连接被频繁关闭。

**原因**：不了解非阻塞 I/O 语义。

**解决**：`EAGAIN/EWOULDBLOCK → Again → 返回 epoll 等待`。

### 错误 9：在 HandlerEvent 中立即 delete TcpConnection

**表现**：偶发崩溃、内存错误、难以复现。

**原因**：内部 Channel 的成员函数还在运行，对象已经释放。

**解决**：只标记待删除，在本轮 `Distribute` 完成后清理。

### 错误 10：先 delete，再 RemoveChannel

**表现**：Epoller 留下悬空 `Channel*`。

**原因**：销毁了被观察对象，却没有先解除观察关系。

**解决**：`RemoveChannel → 解除容器所有权 → delete`。

### 错误 11：一个事件触发多次关闭

**表现**：同一 fd 多次加入待删除队列，重复 `DEL` 或重复 `delete`。

**原因**：`revents_` 可同时包含多个标志；多个处理分支都可能发现关闭。

**解决**：`Connected → Closing` 状态门作为第一层保护，待删除集合去重作为第二层保护。

### 错误 12：状态未初始化

**表现**：`state_ == Connected` 的判断结果随机。

**原因**：基础类型成员未初始化会保留不确定值。

**解决**：在构造函数初始化列表中设置合法初始状态。

### 错误 13：删除后继续使用迭代器或对象

典型错误：

```cpp
delete it->second;
connections_.erase(it);
it->second->SetState(...); // 两层无效访问
```

**原因**：对象已释放，`erase` 后迭代器也失效。

**解决**：删除前完成所有必要操作；删除后不再访问对象；`erase` 后不再访问该迭代器。

### 错误 14：混用不同枚举中的 Close/Closed

**表现**：把 I/O 结果写入连接状态。

**原因**：非限定枚举名称相似、成员类型又使用裸 `int`。

**解决**：采用 `enum class`，Setter 接受具体枚举类型，不接受任意 `int`。

### 错误 15：RemoveChannel 失败仍继续销毁

**表现**：用户态对象消失，但内核或 Epoller 仍保留对应关系。

**原因**：忽略清理操作结果。

**解决**：让删除操作返回明确结果，记录错误，并执行一致的失败策略；至少不能静默假装成功。

### 错误 16：用 fd 永久代表连接身份

**表现**：高频断连重连时，旧清理任务误伤复用同一数字的新连接。

**原因**：fd 是可复用编号，不是永久唯一 ID。

**解决**：当前阶段保证待清理任务在同一轮末尾及时执行；进阶版本使用连接对象身份、智能指针或 generation id。

## 10. 测试方法

### 10.1 建议增加的调试信息

日志至少包含：

```text
fd
Channel 旧状态 → 新状态
epoll_ctl 操作：ADD / MOD / DEL
events / revents
Connection 旧状态 → 新状态
关闭原因
加入待删除集合
真正销毁时间
```

不要只打印“成功”或“失败”，否则难以确认操作顺序。

### 10.2 测试一：单客户端连接

步骤：

1. 启动服务器；
2. 建立一个客户端连接；
3. 暂不发送数据；
4. 检查日志。

期望：

```text
Channel: New → Added
epoll_ctl: ADD 一次
Connection: Connected
```

不应发生重复 `ADD`。

### 10.3 测试二：多次收发

步骤：

1. 同一客户端连续发送多次；
2. 服务器产生响应；
3. 检查可写事件的启用和取消。

期望：

```text
Added 状态保持不变
EnableWrite → MOD
发送完成 DisableWrite → MOD
```

不应因为修改监听事件而再次 `ADD`。

### 10.4 测试三：客户端正常退出

期望顺序：

```text
recv == 0
↓
Connected → Closing
↓
加入待清理集合
↓
HandlerEvent 返回
↓
Distribute 结束
↓
DEL 成功
↓
Added → Deleted
↓
TcpConnection 析构
↓
fd 关闭一次
```

### 10.5 测试四：一次包含多个事件标志

尽量制造客户端发送数据后立即关闭的场景，观察可能出现的 `EPOLLIN | EPOLLHUP`。

期望：

- 可以从多个位置发现关闭；
- `HandleClose` 只通知服务器一次；
- 待删除集合中只有一份；
- 只执行一次 `DEL` 和一次析构。

### 10.6 测试五：连接重置或异常断开

让客户端异常退出，或使用会导致 RST 的关闭方式。

期望：

- 记录具体错误；
- 致命错误进入统一关闭路径；
- 没有只清 buffer 后继续监听的连接。

### 10.7 测试六：EAGAIN

在非阻塞读写循环中观察 `EAGAIN/EWOULDBLOCK`。

期望：

- 不进入 `Closing`；
- 不加入待删除集合；
- 返回 EventLoop，之后仍可继续收发。

### 10.8 测试七：多客户端并发与频繁断连

同时建立多个连接，循环发送、关闭和重连。

检查：

- 一个连接关闭不影响其他连接；
- `connections_` 数量最终回到合理值；
- Epoller 内保存的 Channel 数量与活动连接相符；
- 没有重复 fd 清理和悬空指针迹象。

### 10.9 测试八：系统调用失败路径

通过错误 fd、重复操作或测试替身模拟 `ADD / MOD / DEL` 失败。

期望：

- `ADD` 失败后状态仍为 `New`；
- `MOD` 失败后不伪造成功；
- `DEL` 失败后不把对象当作已经完全脱离 Epoller；
- 日志能指出失败操作、fd 和 errno。

### 10.10 使用内存检查工具

建议在调试版本中使用 AddressSanitizer：

```text
-fsanitize=address,undefined
-fno-omit-frame-pointer
-g
```

重点观察：

- heap-use-after-free；
- double-free；
- 无效内存访问；
- 未定义行为。

也可以配合 Valgrind 检查泄漏和非法访问。工具测试不能替代设计检查，但能有效暴露生命周期错误。

### 10.11 通过结果的标准

不要只以“客户端收到了响应”为通过标准。生命周期测试必须同时证明：

- 状态转换正确；
- 操作顺序正确；
- 错误路径正确；
- 对象只销毁一次；
- 无内存错误；
- 多次、并发和异常场景下行为一致。

## 12. 复习问答

### 1. Channel 为什么需要生命周期状态？

因为 `epoll_ctl` 的 `ADD / MOD / DEL` 依赖 fd 当前是否已经在 epoll 中，而 `events_` 只能表示想监听什么，不能表示注册关系。

### 2. 为什么不能用多个 bool？

多个 bool 可能形成矛盾组合；枚举能保证任一时刻只有一个明确状态。

### 3. 为什么状态只能在 epoll_ctl 成功后修改？

否则系统调用失败时，用户态会记录一个内核中并不存在的状态。

### 4. EnableWrite 会改变 ChannelState 吗？

不会。它只改变 `events_`，Channel 仍然是 `Added`，随后执行 `MOD`。

### 5. 谁拥有 Channel？

当前设计中 `TcpConnection` 拥有 Channel；Epoller 只保存并观察 `Channel*`。

### 6. EAGAIN 为什么不能关闭连接？

它只表示非阻塞操作暂时无法继续，连接本身仍然有效。

### 7. 为什么正常关闭和致命错误要共用关闭路径？

它们的原因不同，但最终都要解除 epoll 关系、移出连接表、销毁对象并关闭 fd。统一路径可以避免遗漏和重复释放。

### 8. 逻辑关闭和物理销毁有什么区别？

逻辑关闭表示连接已不能继续业务并进入 `Closing`；物理销毁表示真正 `DEL`、移出容器、析构对象和关闭 fd。

### 9. 为什么不能在回调中立即 delete？

因为当前 `Channel::HandlerEvent` 或其他回调可能仍在使用该对象，立即删除会造成 use-after-free。

### 10. 为什么 Cleanup 放在 Distribute 后？

此时本轮所有事件回调已经返回，不再处于目标对象的成员函数调用栈中，是更安全的销毁时间点。

### 11. 为什么 ConnectionState 能防止重复关闭？

第一次关闭将 `Connected` 改成 `Closing`；后续请求看到不再是 `Connected`，便直接返回。

### 12. `Closed` 状态一定要设置吗？

不一定。当前实现中对象清理后马上销毁，没有安全观察者读取 `Closed`。保留它可用于未来更复杂的异步生命周期设计。

## 13. 总结

阶段七第一部分的本质是：

> 用 `ChannelState` 保证用户态 Channel 与内核 epoll 的注册关系一致。

你需要牢记：

```text
New → ADD 成功 → Added
Added → MOD 成功 → Added
Added → DEL 成功 → Deleted
```

阶段七第二部分的本质是：

> 把“发现连接需要关闭”和“真正销毁连接”分开。

你需要牢记：

```text
各种关闭原因
↓
统一 HandleClose
↓
Connected → Closing
↓
通知 TcpServer
↓
登记待删除
↓
本轮回调全部结束
↓
RemoveChannel
↓
移出 connections_
↓
销毁 TcpConnection
↓
关闭 fd
```

最后，用一句话概括这两个部分：

> 生命周期管理不是研究“怎样 delete”，而是明确谁拥有资源、状态何时改变，以及什么时候 delete 才安全。

当你能从创建、注册、读写、逻辑关闭一直讲到延迟销毁，并能解释每一步为什么按这个顺序执行，就真正掌握了这一阶段。
