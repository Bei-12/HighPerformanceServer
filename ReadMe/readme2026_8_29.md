# 阶段七第 3～6 部分学习总结

> 面向零基础：从 Buffer、非阻塞 IO，到 `epoll_event.data.ptr`，再到 `eventfd` 唤醒 EventLoop

## 0. 先看全局：这四部分解决什么问题

这四部分不是四个互不相关的小功能，而是一条逐步完善 Reactor 服务器的主线：

```text
第 3 部分：Buffer 抽象
解决“收到的数据放哪里、没发完的数据放哪里”
            ↓
第 4 部分：非阻塞 IO 完善
解决“现在不能继续读/写时，服务器怎样不阻塞、不丢数据”
            ↓
第 5 部分：Epoller data.ptr 优化
解决“epoll 返回事件后，怎样直接找到对应 Channel”
            ↓
第 6 部分：eventfd 唤醒退出
解决“EventLoop 卡在 epoll_wait(-1) 时，另一个线程怎样让它退出”
```

最终数据流是：

```text
客户端
  ↓ TCP 字节流
recv
  ↓
InputBuffer
  ↓
业务处理
  ↓
OutputBuffer
  ↓
send（可能只发送一部分）
  ↓
客户端
```

最终事件流是：

```text
epoll_wait
  ↓ 返回 epoll_event
data.ptr 直接得到 Channel*
  ↓
Channel::HandlerEvent()
  ↓
读 / 写 / 关闭回调
```

# 1. 第三部分：Buffer 抽象

## 1.1 核心目标

Buffer 的目标不只是“把 `std::string` 包进一个类”，而是建立正确的网络数据观念：

> TCP 传输的是字节流。有效数据由“起始地址 + 字节长度”确定，不由 `\0` 确定。

服务器至少需要两个 Buffer：

```text
InputBuffer
  保存 recv 已经收到、业务尚未处理的数据

OutputBuffer
  保存业务已经产生、send 尚未全部发送的数据
```

## 1.2 必须掌握的知识点

### TCP 没有消息边界

客户端一次发送 `hello`，服务器不一定一次收到 `hello`：

```text
send("hello")
    ↓
recv → "he"
recv → "llo"
```

两次发送也可能一次收到：

```text
send("hello")
send("world")
    ↓
recv → "helloworld"
```

前者常被称为“半包”，后者常被称为“粘包”。Buffer 能暂存字节，但它不知道一条业务消息在哪里结束。

```text
Buffer：解决数据暂存
Protocol：解决消息边界
```

因此“有了 Buffer”不等于“已经解决粘包和半包”。以后仍需用固定长度、分隔符或长度字段等协议规则解析消息。

### Buffer 最小接口

第一版无需直接照搬复杂框架，内部用 `std::string` 即可：

```cpp
class Buffer
{
public:
    void Append(const char* data, size_t len)
    {
        data_.append(data, len);
    }

    void Append(const std::string& data)
    {
        data_.append(data);
    }

    const char* Data() const
    {
        return data_.data();
    }

    size_t Size() const
    {
        return data_.size();
    }

    bool Empty() const
    {
        return data_.empty();
    }

    void Retrieve(size_t len)
    {
        if (len >= data_.size())
            data_.clear();
        else
            data_.erase(0, len);
    }

    void RetrieveAll()
    {
        data_.clear();
    }

private:
    std::string data_;
};
```

这里最重要的两个动作是：

```text
Append(data, len)  → 追加 len 个字节
Retrieve(n)        → 消费前 n 个字节
```

## 1.3 关键流程

### 输入流程

```text
recv(fd, temporary, ...)
  ↓ ret > 0
InputBuffer.Append(temporary, ret)
  ↓
业务层查看可读数据
  ↓
处理了 N 字节
  ↓
InputBuffer.Retrieve(N)
```

### 输出流程

```text
业务产生响应
  ↓
OutputBuffer.Append(...)
  ↓
send(OutputBuffer.Data(), OutputBuffer.Size())
  ↓ 实际只发送 ret 字节
OutputBuffer.Retrieve(ret)
  ↓
仍有剩余 → 等下一次可写事件
已经为空 → 停止监听可写事件
```

## 1.4 实际出现过的错误、原因与改法

### 错误 1：用 `strtok` 实现“地址 + 长度”追加

当时写法：

```cpp
void Append(char* data, int ret)
{
    String_ += strtok(data, data + ret);
}
```

为什么错：

- `strtok` 是按“分隔符集合”切割 C 字符串的函数。
- 它的第二个参数应是类似 `" ,"` 的分隔符字符串。
- `data + ret` 是末尾地址，不是分隔符字符串。
- `strtok` 还会修改原始数据，并依赖 C 字符串的 `\0` 结束规则。

正确思维：

```text
data = 起始地址
len  = 有效字节数
```

正确写法：

```cpp
void Append(const char* data, size_t len)
{
    String_.append(data, len);
}
```

### 错误 2：仍用 C 字符串思维追加 `recv` 数据

曾使用过类似思路：

```cpp
rec_buffer_[ret] = 0;
input_buffer_.Append(std::string(rec_buffer_));
```

为什么错：如果网络数据内部本来包含真实 NUL 字节：

```text
A B [0] C D
```

从 `const char*` 构造字符串时会在 `[0]` 处停止，后面的 `C D` 丢失。

改法：永远使用 `recv` 的返回值：

```cpp
ssize_t ret = recv(fd_, rec_buffer, sizeof(rec_buffer), 0);
if (ret > 0)
    input_buffer_.Append(rec_buffer, static_cast<size_t>(ret));
```

### 错误 3：`std::string("hello\0world")` 被截断

当时客户端写法：

```cpp
send_buffer_ = "hello\0world\0";
```

看起来像 12 字节，实际通常只有：

```text
"hello"
size() == 5
```

原因：该赋值使用 `const char*` 重载，按 C 字符串规则在第一个 `\0` 结束。

改法：显式提供长度：

```cpp
std::string send_buffer("hello\0world\0", 12);
```

也可以用明确的字节容器构造。发送时必须用：

```cpp
send(fd, send_buffer.data(), send_buffer.size(), 0);
```

不能用 `strlen(send_buffer.data())`。

### 错误 4：在终端输入 `hello\0world`，以为输入了 NUL

键盘输入的 `\` 和 `0` 是两个可见字符：

```text
'\' + '0'  ≠  0x00
```

真正的 NUL 必须由程序在内存中构造。并且不能只观察终端文本，因为 NUL 不可见，应检查长度与每个字节的整数值。

### 错误 5：误解 `std::string::erase(begin, end)`

曾设计：

```cpp
void Retrieve(int begin, int end)
{
    String_.erase(begin, end);
}
```

但 `erase` 的第二个参数是“删除数量”，不是“结束下标”。

```cpp
erase(2, 5); // 从下标 2 开始删除 5 个字符
```

Buffer 的实际需求是消费前 N 字节，所以接口应简化为：

```cpp
void Retrieve(size_t n)
{
    String_.erase(0, n);
}
```

### 错误 6：收到 CLOSE 就清空已读数据

可能出现：

```text
第一次 recv → "hello" → 已进入 InputBuffer
第二次 recv → 0       → 对端关闭写端
```

如果此时无条件 `Clear()`，已经收到的 `hello` 也被删掉。

要分清：

```text
recv == 0
表示以后没有新数据

不表示
之前已经收到的数据无效
```

是否处理最后一批数据由协议和关闭策略决定，但不能把“连接关闭”和“历史数据作废”混为一谈。

## 1.5 测试方法

### Buffer 单元测试

至少检查：

```text
Append("abc", 3)      → Size == 3
再次 Append("de", 2)  → 内容为 abcde
Retrieve(2)           → 内容为 cde
RetrieveAll()         → Empty == true
```

### 真实 NUL 字节测试

客户端：

```cpp
std::string data("hello\0world\0", 12);
std::cout << data.size() << std::endl; // 应为 12
```

完整验证链：

```text
客户端原始长度             = 12
send 使用的长度            = 12
服务器累计 InputBuffer 长度 = 12
回显后客户端累计接收长度     = 12（若只回显原数据）
第 6、12 个字节的数值       = 0
```

对应字节值：

```text
104 101 108 108 111 0 119 111 114 108 100 0
 h   e   l   l   o  NUL w   o   r   l   d  NUL
```

### 多次追加测试

模拟 TCP 分段：

```text
Append("he", 2)
Append("llo", 3)
最终 Size == 5，内容为 hello
```

## 1.6 验收标准

- 能解释 TCP 为什么需要 Buffer。
- InputBuffer 和 OutputBuffer 职责清晰。
- `Append` 使用“地址 + 长度”，内部 NUL 不会截断。
- `Retrieve(n)` 只消费已处理或已发送的 n 字节。
- 多次 Append 后数据顺序正确。
- 理解 Buffer 不等于协议解析。
- 真实 NUL 测试长度与逐字节值正确。

## 1.7 容易混淆的点

```text
终端显示的 "\0"  ≠ 内存中的 NUL
std::string 能存 NUL，但错误的构造方式会提前截断
send 成功 N 字节   ≠ 对端应用已经读取 N 字节
Buffer             ≠ 消息协议
Retrieve(n)        = 消费前 n 字节，不是删除到下标 n
```

# 2. 第四部分：非阻塞 IO 完善

## 2.1 核心目标

非阻塞服务器不能假设：

```text
一次 recv 就读完
一次 send 就发完
系统调用失败就是连接坏了
```

目标是让每个连接“能做多少做多少”，暂时不能继续时返回 EventLoop，让其他连接运行。

## 2.2 返回值和 `errno` 的基础规则

对 `recv`：

```text
ret > 0  → 收到了 ret 字节
ret == 0 → 对端正常关闭了发送方向
ret < 0  → 此时才检查 errno
```

对 `send`：

```text
ret > 0  → 内核接收了 ret 字节，可能少于请求长度
ret < 0  → 此时才检查 errno
```

关键原则：

> `errno` 只在系统调用明确失败时才有意义。成功后不能读取旧的 `errno` 判断本次结果。

## 2.3 `EAGAIN`、`EINTR`、partial write

### `EAGAIN / EWOULDBLOCK`

读路径：

```text
recv → -1, errno == EAGAIN
= 当前接收缓冲区已经读空
= 本轮读取完成，回到 epoll_wait
```

写路径：

```text
send → -1, errno == EAGAIN
= 当前发送缓冲区暂时满
= OutputBuffer 原样保留
= 保持 EPOLLOUT，稍后再写
```

它不是致命错误，也不代表连接关闭。

### `EINTR`

```text
系统调用尚未完成
  ↓ 被信号打断
返回 -1，errno == EINTR
  ↓
重试同一个操作
```

`EINTR` 不表示成功收到数据，也不表示应该等待下一次 IO 事件。

### partial write

假设 OutputBuffer 有 5 MB：

```text
请求 send 5242880 字节
实际 ret = 2539008
```

这不是错误。它表示内核本次只接受了前 2539008 字节：

```text
OutputBuffer.Retrieve(2539008)
剩余 2703872 字节继续保留
等待下一次 EPOLLOUT
```

## 2.4 关键读流程

```text
EPOLLIN
  ↓
ReadHandler 循环 recv
  ├─ ret > 0
  │    Append(data, ret)
  │    continue
  │
  ├─ EINTR
  │    continue（立即重试）
  │
  ├─ EAGAIN / EWOULDBLOCK
  │    本轮读完，退出读取循环
  │    有数据则进入业务处理
  │
  ├─ ret == 0
  │    对端关闭，进入关闭流程
  │
  └─ 其他错误
       当前连接进入关闭流程
```

一个简化实现：

```cpp
while (true)
{
    char buf[4096];
    ssize_t ret = recv(fd_, buf, sizeof(buf), 0);

    if (ret > 0)
    {
        input_buffer_.Append(buf, static_cast<size_t>(ret));
        continue;
    }

    if (ret == 0)
    {
        CloseHandler();
        return;
    }

    if (errno == EINTR)
        continue;

    if (errno == EAGAIN || errno == EWOULDBLOCK)
        break;

    CloseHandler();
    return;
}
```

## 2.5 关键写流程

```text
OutputBuffer 有数据
  ↓ EnableWrite
EPOLLOUT
  ↓
send
  ├─ ret > 0
  │    Retrieve(ret)
  │    ├─ 仍有数据 → 保持 EPOLLOUT
  │    └─ 已为空   → DisableWrite
  │
  ├─ EINTR
  │    立即重试
  │
  ├─ EAGAIN / EWOULDBLOCK
  │    保留数据、保持 EPOLLOUT、返回 EventLoop
  │
  └─ EPIPE / ECONNRESET / 其他致命错误
       只关闭当前连接
```

关键代码思想：

```cpp
ssize_t ret = send(fd_, output_buffer_.Data(), output_buffer_.Size(), 0);

if (ret > 0)
{
    output_buffer_.Retrieve(static_cast<size_t>(ret));
    if (output_buffer_.Empty())
        channel_.DisableWrite();
    return;
}

if (ret < 0 && errno == EINTR)
{
    // 重试
}
else if (ret < 0 && (errno == EAGAIN || errno == EWOULDBLOCK))
{
    // 不消费 Buffer，等待下一次 EPOLLOUT
}
else
{
    // 当前连接关闭
}
```

## 2.6 实际出现过的错误、原因与改法

### 错误 1：把 `EINTR` 返回成 `DATA`

当时读写代码中出现：

```cpp
if (errno == EINTR)
    return DATA;
```

为什么错：`DATA` 被 Handler 理解为“本次取得数据/发送完成”，但 `EINTR` 表示操作被打断，本次并未完成。语义完全相反。

改法：增加明确的 `RETRY`，或者直接在 IO 函数内部 `continue` 重试：

```text
EINTR → RETRY → Handler continue → 再调用 Read/Write
```

### 错误 2：混淆 `ret` 与 `errno`

正确判断顺序必须是：

```text
先看 ret
ret < 0 时才看 errno
```

不能把返回值与错误码混着比较，也不能在成功后根据旧 `errno` 做决定。`errno` 不会在成功调用后自动清零。

### 错误 3：只判断 `EPIPE`，却没有规避 `SIGPIPE`

曾在 `send` 失败后判断：

```cpp
else if (errno == EPIPE)
    return ERROR;
```

后半段没错，但还不够。写入已关闭 socket 时，系统可能先给进程发送 `SIGPIPE`；默认动作可能直接终止整个服务器，程序甚至来不及检查 `errno`。

完整处理有两层：

```text
第一层：禁止 SIGPIPE 杀死整个进程
第二层：send 失败后根据 EPIPE 等错误关闭当前连接
```

本项目测试采用进程级忽略：

```cpp
#include <signal.h>

int main()
{
    signal(SIGPIPE, SIG_IGN);
    // 启动服务器
}
```

另一种 Linux 思路是单次 `send` 使用 `MSG_NOSIGNAL`。学习项目选择一种即可。

### 错误 4：把 partial write 当成失败，或丢掉剩余数据

```text
ret > 0 但 ret < OutputBuffer.Size()
```

表示部分发送成功，不是错误。只能消费已经发送的 `ret` 字节：

```cpp
output_buffer_.Retrieve(ret);
```

不能 `RetrieveAll()`，也不能重新发送 Buffer 头部，否则会丢数据或重复数据。

### 错误 5：遇到 `EAGAIN` 仍在当前函数中忙等

非阻塞 Reactor 的价值就在于：

```text
当前连接暂时写不了
→ 保留数据
→ 返回 EventLoop
→ 处理其他连接
→ 等 EPOLLOUT 再继续
```

如果在当前 Handler 中不停重试 `EAGAIN`，会空转占用 CPU，并饿死其他连接。

### 错误 6：发送完后 `while` 没有 `return` 或没有关闭 `EPOLLOUT`

成功路径若只是修改状态，却继续循环，可能再次对空 Buffer 调用 `send`，或反复触发 Handler。

正确结束条件：

```text
OutputBuffer 为空
→ DisableWrite()
→ return
```

对函数返回类型也一样：声明为 `int` 就必须保证所有成功路径返回值；否则是未定义行为。若上层不需要结果，更适合改成 `void` 并在内部处理。

### 错误 7：日志打印了错误的 Buffer

业务处理后 `InputBuffer` 已被清空，但 `WriteHandler` 打印的仍是：

```cpp
input_buffer_.GetString()
```

于是出现“Message send to client”后内容为空。这是日志对象错误，不代表没有发送数据。写路径应观察：

```text
OutputBuffer 发送前大小
send 返回值
Retrieve 后剩余大小
```

### 错误 8：客户端出错后仍打印 `client send finished`

5 MB 测试时，客户端在只发送约 4 MB 后遇到 `Connection reset by peer`，但循环退出后仍无条件打印 “finished”。

日志必须与状态一致：

```text
total == target size → send finished
中途 ret < 0        → send failed / interrupted
```

## 2.7 大数据与 partial write 测试

### 为什么几 KB 不够

测试中 3555、4115 字节都被一次 `send` 完整接受：

```text
before == send ret
```

这只能验证普通发送，无法证明 partial write 路径。

### 自动生成 5 MB 数据

客户端：

```cpp
std::string data(5 * 1024 * 1024, 'A');
```

客户端自己的 `send` 也可能部分发送，因此也要循环：

```cpp
size_t total = 0;
while (total < data.size())
{
    ssize_t ret = send(fd,
                       data.data() + total,
                       data.size() - total,
                       0);
    if (ret > 0)
        total += static_cast<size_t>(ret);
    else
        break; // 测试程序中还应细分 EINTR 等情况
}
```

为了更容易让服务器写缓冲区受压：

```text
客户端循环发送完整 5 MB
  ↓
客户端故意暂时不 recv（例如等待几秒）
  ↓
服务器产生大 OutputBuffer
  ↓
服务器 send 出现 partial write / EAGAIN
```

服务器应打印：

```text
before: 2643161
send ret: 2539008
after: 104153
PARTIAL WRITE
```

之后：

```text
客户端开始 recv
  ↓
发送窗口恢复
  ↓
EPOLLOUT 再次触发
  ↓
继续发送剩余数据
  ↓
after: 0
  ↓
DisableWrite
```

本次实际测试已经观察到 partial write，例如 `before` 大于 `send ret`，随后多轮发送，最终又出现 `before == send ret`，证明剩余数据被继续发送完毕。

### 多客户端测试

同时启动两个 5 MB 客户端：

```text
客户端 A 暂时写不动
  ↓ 服务器回到 EventLoop
客户端 B 仍能读写
  ↓
A 后续收到 EPOLLOUT 再继续
```

这是验证“一个慢连接不能拖死整个服务器”的关键测试。

### 异常断连与 SIGPIPE 测试

```text
1. main 中忽略 SIGPIPE
2. 启动 server、client A、client B
3. A 触发大响应，并暂时不接收
4. 在服务器仍有待发送数据时强制结束 A
5. 观察 A 对应连接被关闭
6. 立刻让 B 继续 send/recv
```

不要求一定精确看到 `EPIPE`；还可能先看到 `ECONNRESET`、`recv == 0`、`EPOLLHUP` 或 `EPOLLRDHUP`。核心验收是：

```text
异常客户端被清理
服务器进程仍然存活
其他客户端继续正常通信
```

## 2.8 验收标准

- `recv` 循环读到 `EAGAIN` 后正常返回 EventLoop。
- `EINTR` 会重试，不会被当成 `DATA`。
- partial write 后只消费实际发送字节。
- `EAGAIN` 时 OutputBuffer 保持不变，并继续监听 `EPOLLOUT`。
- OutputBuffer 清空后 `DisableWrite()` 并返回。
- 5 MB 测试最终不丢、不重、不乱序。
- 两个大客户端之间不会互相阻塞。
- 异常断连不会杀死整个服务器。

## 2.9 容易混淆的点

```text
Read EAGAIN  = 当前没更多数据可读
Write EAGAIN = 当前没更多空间可写

EINTR  = 被信号打断，应重试
EAGAIN = 暂时做不了，应等待下一次就绪

partial write = 成功发送一部分
EAGAIN         = 本次一字节也没继续写入

send 返回 N = 内核接受 N 字节
不等于对端应用已经读取 N 字节
```

# 3. 第五部分：Epoller 从 `data.fd` 优化到 `data.ptr`

## 3.1 核心目标

旧事件查找路径：

```text
epoll_wait
  ↓
event.data.fd
  ↓
unordered_map<fd, Channel*>::find(fd)
  ↓
Channel*
```

新路径：

```text
epoll_wait
  ↓
event.data.ptr
  ↓
Channel*
```

一句话：让 epoll 返回的不只是“哪个 fd 就绪”，而是直接返回“哪个 Channel 就绪”。

## 3.2 知识点：`epoll_event.data` 是 union

它可以保存 fd，也可以保存指针，但同一次只能按一种方式解释：

```cpp
event.data.fd = fd;
```

或：

```cpp
event.data.ptr = channel;
```

`data.ptr` 的类型是 `void*`，取出时转换回 `Channel*`：

```cpp
auto* channel = static_cast<Channel*>(events_[i].data.ptr);
```

## 3.3 三个关键修改点

### ADD

```cpp
epoll_event ev{};
ev.events = channel->Events();
ev.data.ptr = channel;
epoll_ctl(epfd_, EPOLL_CTL_ADD, channel->Fd(), &ev);
```

### MOD

`EPOLL_CTL_MOD` 也必须继续填 `data.ptr`：

```cpp
epoll_event ev{};
ev.events = channel->Events();
ev.data.ptr = channel;
epoll_ctl(epfd_, EPOLL_CTL_MOD, channel->Fd(), &ev);
```

不能只在 ADD 时设置，然后假定 MOD 自动保留旧指针。

### Poll

```cpp
std::vector<Channel*> active;
int count = EpollWait();

for (int i = 0; i < count; ++i)
{
    auto* channel = static_cast<Channel*>(events_[i].data.ptr);
    channel->SetRevents(events_[i].events);
    active.push_back(channel);
}
```

## 3.4 这不是智能指针优化

实际学习中曾问：“第五部分是用智能指针实现吗？”

答案是否定的：

```text
data.ptr 优化：解决事件定位
智能指针：解决对象所有权与生命周期
```

当前架构中：

```text
TcpConnection owns Channel
Epoller observes Channel*
```

Epoller 不负责 `delete Channel`，因此裸指针能表达“非拥有观察关系”。`epoll_event.data.ptr` 也不会自动维护 `shared_ptr` 引用计数。

## 3.5 最大风险：悬空指针

内核记录了 `Channel*` 后，Channel 必须活得足够久：

```text
TcpConnection 准备销毁
  ↓
RemoveChannel
  ↓
EPOLL_CTL_DEL 成功
  ↓
本轮事件分发结束 / 延迟销毁
  ↓
delete TcpConnection
  ↓
Channel 随之析构
```

绝对不能：

```text
先 delete TcpConnection
  ↓ Channel 已销毁
epoll 中仍保留 Channel*
  ↓
下一次 data.ptr 得到悬空指针
  ↓
未定义行为 / 崩溃
```

## 3.6 实际出现过的错误、原因与改法

### 错误 1：只修改 ADD，没有统一修改 MOD

每次传给 `epoll_ctl` 的事件描述都应完整设置：

```text
events = Channel 当前关心的事件
data.ptr = Channel 地址
```

ADD 和 MOD 必须一致。

### 错误 2：`RemoveChannel()` 删除失败仍返回 `true`

曾有逻辑：

```cpp
if (Del(fd))
{
    channels_.erase(fd);
    channel->SetState(DELETED);
}
return true;
```

如果 `Del(fd)` 失败，函数仍返回 `true`，上层可能误以为内核已不再持有 `Channel*`，进而销毁对象。

正确语义：

```cpp
bool RemoveChannel(Channel* channel)
{
    if (channel->State() != ADDED)
        return true; // 需按项目状态机定义

    if (!Del(channel->Fd()))
        return false;

    channels_.erase(channel->Fd());
    channel->SetState(DELETED);
    return true;
}
```

最重要的是：

```text
DEL 成功 → true → 才能进入销毁阶段
DEL 失败 → false → 不能假装已经安全删除
```

### 错误 3：认为切到 `data.ptr` 后必须立刻删除 `channels_`

事件分发已经不再需要 map 查找，但 map 仍可暂时用于：

- 记录当前注册的 Channel；
- 调试和一致性检查；
- 项目中其他按 fd 查找的逻辑。

可以先保留，等所有用途消失后再删除，不需要为了“优化完成”强行删除。

### 错误 4：忽视 Channel 生命周期

`data.ptr` 并不拥有对象，也不保证地址有效。优化后生命周期要求反而更直观、更严格。之前完成的 `RemoveChannel + 延迟销毁` 正是这一步的安全基础。

## 3.7 测试方法

按风险逐级测试：

```text
1. 单客户端连接、收发、正常断开
2. 两个客户端同时收发
3. A 断开后，B 继续正常工作
4. 两个 5 MB 客户端同时传输
5. 检查关闭时没有段错误、double free、Bad file descriptor
```

可以临时打印：

```text
注册时：fd、Channel 地址
事件返回：data.ptr 转换后的 Channel 地址
删除时：fd、Channel 地址、DEL 结果
```

同一连接的地址应一致；DEL 失败不得进入销毁阶段。

## 3.8 验收标准

- ADD 和 MOD 都设置 `data.ptr = channel`。
- Poll 不再通过 fd 查 map 才得到 Channel。
- `SetRevents` 和事件分发正常。
- `RemoveChannel` 返回值与真实 DEL 结果一致。
- Channel 在 DEL 成功前绝不销毁。
- 单客户端、多客户端、断连、大数据测试全部正常。

## 3.9 容易混淆的点

```text
data.ptr 是事件定位，不是所有权管理
裸指针不等于一定错误，关键是生命周期契约
切换 data.ptr 不等于必须删除 channels_ map
DEL fd 与 delete Channel 是两个动作
必须先 DEL，再销毁对象
```

# 4. 第六部分：EventLoop 使用 `eventfd` 唤醒并退出

## 4.1 核心目标

EventLoop 通常会阻塞在：

```cpp
epoll_wait(epfd, events, maxevents, -1);
```

如果另一个线程只做：

```cpp
running_ = false;
```

Loop 线程仍睡在 `epoll_wait`，没有机会再次检查 `running_`。

目标是：

> 让另一个线程制造一个 epoll 能看到的事件，使 `epoll_wait` 立即返回。

## 4.2 `eventfd` 的直觉

可以把 `eventfd` 想成一个由内核管理的 64 位计数器：

```text
初始 counter = 0 → 不可读
write(uint64_t 1) → counter 增加 → 变为可读 → EPOLLIN
read(uint64_t)    → 消费计数       → 重新不可读
```

它像一只铃铛：

```text
write = 按铃
read  = 处理铃声
EnableRead = 告诉 epoll“铃响时通知我”
```

## 4.3 完整关键流程

```text
Loop 线程
EventLoop::Loop()
  ↓
epoll_wait(-1) 阻塞

另一个线程
Quit()
  ↓
atomic running_ = false
  ↓
WakeUp()
  ↓
write(wakefd_, uint64_t 1)
  ↓
eventfd 变为可读

Loop 线程
epoll_wait 返回
  ↓
wakechannel_ 收到 EPOLLIN
  ↓
WakeUpHandler()
  ↓
read(wakefd_)
  ↓
Distribute() 结束
  ↓
while 再检查 running_
  ↓ false
Loop 退出
```

## 4.4 初始化顺序

```text
创建 eventfd
  ↓ 成功得到真实 fd
设置 wakechannel_ 的 fd
  ↓
绑定 ReadCallback → WakeUpHandler
  ↓
通过 EventLoop::AddChannel 统一注册
  ↓
EnableRead / 加入 epoll
```

示意代码：

```cpp
EventLoop::EventLoop()
    : running_(false), wakefd_(-1)
{
    wakefd_ = eventfd(0, EFD_NONBLOCK | EFD_CLOEXEC);
    if (wakefd_ < 0)
    {
        std::cerr << strerror(errno) << std::endl;
        std::exit(1);
    }

    wakechannel_.SetFd(wakefd_);
    wakechannel_.SetReadCallback([this]
    {
        WakeUpHandler();
    });
    wakechannel_.EnableRead();
    AddChannel(&wakechannel_);
}
```

如果项目中 `EnableRead()` 会立刻触发 update callback，需根据 Channel 的实际状态机调整“设置回调、AddChannel、EnableRead”的先后；不变的原则是：注册前 fd 必须有效，Channel 必须拥有正确的 EventLoop 更新路径。

## 4.5 `WakeUp` 与 `WakeUpHandler`

```cpp
void WakeUp()
{
    uint64_t one = 1;

    while (true)
    {
        ssize_t ret = write(wakefd_, &one, sizeof(one));

        if (ret == sizeof(one))
            return;

        if (ret < 0 && errno == EINTR)
            continue;

        if (ret < 0 && errno == EAGAIN)
            return; // 通常表示已有待处理唤醒，fd 已处于可读状态

        std::cerr << "eventfd write failed: "
                  << strerror(errno) << std::endl;
        return;
    }
}
```

```cpp
void WakeUpHandler()
{
    uint64_t value = 0;

    while (true)
    {
        ssize_t ret = read(wakefd_, &value, sizeof(value));

        if (ret == sizeof(value))
            return;

        if (ret < 0 && errno == EINTR)
            continue;

        if (ret < 0 && errno == EAGAIN)
            return;

        std::cerr << "eventfd read failed: "
                  << strerror(errno) << std::endl;
        return;
    }
}
```

## 4.6 跨线程状态

普通 `bool` 被两个线程同时读写会产生 data race：

```text
Loop 线程读 running_
Quit 线程写 running_
```

因此使用：

```cpp
std::atomic<bool> running_{false};
```

这里 `atomic` 解决的是 `running_` 的跨线程访问安全，`eventfd` 解决的是把阻塞中的 Loop 线程叫醒。两者职责不同，缺一不可。

## 4.7 实际出现过的错误、原因与改法

### 错误 1：eventfd 尚未创建就 `SetFd(-1)`

当时初始化：

```cpp
wakefd_ = -1;
wakechannel_.SetFd(wakefd_);
poller_.AddChannel(&wakechannel_);
```

实际链条是：

```text
wakefd = -1
→ Channel fd = -1
→ 尝试把无效 fd 加入 epoll
```

改法：先调用 `eventfd(...)`，检查成功后再设置 Channel。

### 错误 2：用 `EnableWrite()` 实现 WakeUp

当时写法：

```cpp
void WakeUp()
{
    wakechannel_.EnableWrite();
}
```

为什么错：`EnableWrite()` 只是让 epoll 开始关心该 fd 的 `EPOLLOUT`，并没有向 eventfd 写入计数，也没有制造预期的 `EPOLLIN`。

正确关系：

```text
WakeUp()        → write(wakefd_)
WakeUpHandler() → read(wakefd_)
```

### 错误 3：WakeUpHandler 再次 `EnableRead()`

`wakechannel_` 本来就应持续监听读事件。Handler 的职责是读取并消费 eventfd 计数，否则 fd 会一直可读，`epoll_wait` 可能反复立即返回，造成 CPU 空转。

### 错误 4：手动析构成员 Channel

当时析构中写过：

```cpp
wakechannel_.~Channel();
```

成员对象会在 `EventLoop` 析构时自动析构。手动调用后，编译器还会再次自动析构，存在重复析构和未定义行为风险。

正确生命周期：

```text
RemoveChannel(&wakechannel_)
  ↓
close(wakefd_)
  ↓
EventLoop 析构其余成员
  ↓
wakechannel_ 自动析构
```

### 错误 5：`eventfd()` 失败后仍继续构造

若创建失败但对象仍然存在，后续 `Quit()` 会尝试：

```cpp
write(-1, ...);
```

eventfd 是该设计的必要组成部分，创建失败应打印真实错误并终止初始化或抛出异常，不能静默降级。

成功判断应为：

```cpp
wakefd_ >= 0
```

而不是 `wakefd_ > 0`，因为 fd 0 理论上也是合法描述符。

### 错误 6：把 eventfd 的 `EINTR` 返回给无人处理的上层

曾让 `WakeUp()` 返回 `RETRY`，但 `Quit()` 没接收返回值：

```text
write 被 EINTR 打断
→ WakeUp 返回 RETRY
→ Quit 忽略结果
→ 没有真正写入 eventfd
→ Loop 仍可能睡在 epoll_wait
```

改法：`WakeUp` 与 `WakeUpHandler` 在函数内部循环消化 `EINTR`。

### 错误 7：返回类型为 `int`，成功路径没有 return

曾出现：

```cpp
int WakeUp()
{
    // 失败分支 return
    // 成功分支无 return
}
```

非 `void` 函数走到末尾而不返回值是未定义行为。本项目中上层不需要状态值，更适合使用 `void` 并在内部完成重试和日志。

### 错误 8：`cleanup_()` 没判空

最小 EventLoop 测试没有 TcpServer 注册 cleanup callback，直接调用空的 `std::function` 会抛 `std::bad_function_call`。

改法：

```cpp
if (cleanup_)
    cleanup_();
```

### 错误 9：`EpollWait()` 把所有 `ret < 0` 都当成同一种情况

`epoll_wait` 也可能被信号打断：

```cpp
while (true)
{
    int ret = epoll_wait(epfd_, events_, NUM, -1);
    if (ret >= 0)
        return ret;

    if (errno == EINTR)
        continue;

    std::cerr << strerror(errno) << std::endl;
    std::exit(1);
}
```

日志也应在排除 `EINTR` 后再打印，否则会把可恢复中断误报成严重错误。

### 错误 10：在同一个线程里先 `Loop()`，再 `Quit()`

曾尝试：

```cpp
loop.Loop();
sleep(2);
loop.Quit();
```

但 `Loop()` 已阻塞在 `epoll_wait(-1)`，后两行永远执行不到。测试必须使用两个线程。

### 错误 11：使用 `std::thread` 时缺少 `-pthread`

实际报错：

```text
terminate called after throwing an instance of 'std::system_error'
what(): Enable multithreading to use std::thread: Operation not permitted
```

原因不是 EventLoop 或 eventfd 逻辑，而是编译链接没有正确启用线程支持。

改法：

```bash
g++ -o server ServerMain.cc -g -std=c++11 -pthread
```

Makefile 中同样要加 `-pthread`，然后彻底重新编译。

## 4.8 最小测试方法

```cpp
int main()
{
    signal(SIGPIPE, SIG_IGN);

    EventLoop loop;

    std::thread t([&loop]
    {
        std::cout << "EventLoop start" << std::endl;
        loop.Loop();
        std::cout << "EventLoop quit" << std::endl;
    });

    sleep(2);
    std::cout << "Call Quit" << std::endl;
    loop.Quit();

}
```

编译时加 `-pthread`。

```text

Loop start
Epoll wait 前

（约 2 秒后）

WakeUp write 成功
WakeHandler 调用成功
Loop End
EventLoop quit
```

## 4.9 进阶测试

### 重复唤醒

连续调用多次 WakeUp，确认：

```text
Loop 能醒来
Handler 能消费 eventfd
不会无限触发读事件
之后还能重新进入 epoll_wait
```

### 真实服务器退出

```text
启动 server
连接 client A、client B
正常通信
触发 loop.Quit()
```

退出阶段不应出现：

```text
Segmentation fault
double free
Del fd failed
Bad file descriptor
```

析构顺序应为：

```text
停止事件循环
→ Remove wakechannel
→ close wakefd
→ Channel 自动析构
```

## 4.10 验收标准

- `eventfd` 在设置 Channel fd 之前成功创建。
- wake Channel 监听 `EPOLLIN`，回调会 `read(eventfd)`。
- `Quit()` 先令原子 `running_` 为 false，再 `write(eventfd)`。
- Loop 即使阻塞在 `epoll_wait(-1)`，也能在 Quit 后立即返回并退出。
- `EINTR` 在函数内部重试，`EAGAIN` 被合理处理。
- cleanup callback 判空。
- 析构前先从 epoll 删除 wake Channel，再关闭 fd。
- 无手动析构、无 double free、无无效 fd 操作。
- 线程测试使用 `-pthread` 并能 `join` 完成。

## 4.11 容易混淆的点

```text
running_ = false 只改变状态，不会自动唤醒 epoll_wait
atomic 解决数据竞争，eventfd 解决阻塞唤醒
WakeUp 不是 EnableWrite，而是 write(eventfd)
WakeUpHandler 不是 EnableRead，而是 read(eventfd)
eventfd 读写的是 uint64_t，不是字符串
EAGAIN 在 eventfd write 中通常表示已有待消费通知
成员对象不需要手动调用析构函数
```
