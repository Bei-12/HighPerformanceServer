# 阶段六：Reactor模型（一）------ Channel 与 TcpConnection设计总结

## 一、阶段六目标

阶段五完成了非阻塞TCP服务器：

-   socket
-   bind
-   listen
-   accept
-   recv/send
-   epoll多路复用
-   EPOLLIN/EPOLLOUT
-   EAGAIN处理
-   输入输出缓冲区

但是阶段五中TcpServer承担了太多职责：

    TcpServer
     ├── accept
     ├── epoll_wait
     ├── recv
     ├── send
     ├── buffer管理
     └── 业务处理

代码耦合较高。

阶段六开始引入Reactor思想：

    事件检测
        ↓
    事件分发
        ↓
    对象处理自己的业务

------------------------------------------------------------------------

# 二、Reactor模型

Reactor核心思想：

> 等待事件发生，事件发生后调用对应处理函数。

整体结构：

    Poller
     |
     | 负责epoll_wait
     ↓
    Channel
     |
     | 负责事件和回调
     ↓
    TcpConnection

    负责：
    recv
    send
    buffer
    业务处理

------------------------------------------------------------------------

# 三、为什么需要Channel？

epoll只能知道：
    fd发生了什么事件

例如：

    fd=5
    EPOLLIN

但是epoll不知道：

    fd=5属于哪个TcpConnection
    发生事件后调用哪个函数

所以增加Channel：

    fd
    +
    事件
    +
    回调函数

作为桥梁。

------------------------------------------------------------------------

# 四、Channel负责什么？

## 1. 保存fd

每个Channel对应一个文件描述符。

    Channel
     |
     fd

------------------------------------------------------------------------

## 2. 保存关注事件events\_

表示：

> 希望内核通知我的事件

例如：

    EPOLLIN

表示关注读事件。

    EPOLLIN | EPOLLOUT

表示同时关注读写事件。

注意：

events_表示关注什么，不表示已经发生。

------------------------------------------------------------------------

## 3. 保存实际发生事件revents\_

epoll_wait返回：

    events[i].events

表示：

真正发生的事件。

例如：

    revents = EPOLLIN

说明：

客户端发送数据。

------------------------------------------------------------------------

# 五、为什么使用回调？

阶段五：

    TcpServer判断事件

    if EPOLLIN:
        ReadHandler

    if EPOLLOUT:
        WriteHandler

问题：

TcpServer知道所有业务。

Reactor希望：

    Channel发现事件

    ↓

    通知TcpConnection

因此使用回调。

------------------------------------------------------------------------

# 六、lambda绑定成员函数

TcpConnection:

    ReadHandler()

但是Channel不知道对象是谁。

例如：

    client1
     |
     TcpConnection1


    client2
     |
     TcpConnection2

所以使用lambda捕获this：

``` cpp
[this]()
{
    this->ReadHandler();
}
```

含义：

保存当前对象地址。

以后调用：

    lambda()

等价：

    当前对象.ReadHandler()

------------------------------------------------------------------------

# 七、std::function作用

function可以保存：

-   普通函数
-   lambda
-   函数对象

例如：

``` cpp
function<void()> readCallback;
```

表示：

保存一个：

    无参数
    无返回值

的可调用对象。

------------------------------------------------------------------------

# 八、当前设计流程

## 读事件流程

    客户端发送数据

    ↓

    epoll_wait检测EPOLLIN

    ↓

    Poller更新Channel

    ↓

    Channel调用readCallback

    ↓

    lambda调用TcpConnection::ReadHandler

    ↓

    recv读取数据

------------------------------------------------------------------------

## 写事件流程

    output_buffer存在数据

    ↓

    Channel关注EPOLLOUT

    ↓

    epoll返回写事件

    ↓

    Channel调用writeCallback

    ↓

    TcpConnection发送数据

------------------------------------------------------------------------

# 九、阶段六遇到的问题

## 问题1：为什么不用继承？

错误：

    Channel继承TcpConnection

原因：

二者不是"is-a"关系。

正确：

    TcpConnection拥有Channel

属于组合关系。

------------------------------------------------------------------------

## 问题2：TcpConnection为什么不能直接操作epoll？

阶段五：

    TcpServer
        |
     epoller.Mod()

可以。

阶段六：

职责分离。

TcpConnection不应该知道：

-   epoll
-   Poller
-   EventLoop

应该：

    TcpConnection
          |
          ↓
         Channel
          |
          ↓
        Poller

------------------------------------------------------------------------

## 问题3：close在哪里处理？

阶段五：

    发现关闭
     ↓
    删除epoll
     ↓
    close(fd)

阶段六不能简单：

    TcpConnection直接close(fd)

因为Channel还管理这个fd。

未来应该增加：

    closeCallback

流程：

    TcpConnection发现关闭

    ↓

    closeCallback

    ↓

    EventLoop/Poller处理

    ↓

    删除Channel

    ↓

    关闭fd

------------------------------------------------------------------------

# 总结

阶段五解决：

> 一个服务器如何处理多个客户端。

阶段六解决：

> 如何让服务器结构清晰、可扩展。

核心变化：

以前：

    TcpServer负责全部工作

现在：

    Poller负责等待事件

    Channel负责事件分发

    TcpConnection负责连接业务
