TCP线程池服务器实践

一、项目目标

在完成TCP基础、多客户端TCP服务器之后，实现基于线程池的TCP服务器。

目标：
多客户端连接
线程复用
阻塞队列管理任务
生产者消费者模型

二、服务器演进

1. 单客户端TCP
流程：
socket -> bind -> listen -> accept -> recv/send
问题：一个客户端阻塞后无法处理其他客户端。

2. 多客户端TCP
模型：
主线程:
accept()
工作线程:
recv/send

问题：
客户端增加时线程数量增加，资源消耗大。
因此引入线程池。

三、线程池服务器结构

TcpServer
    |
 accept()
    |
 TcpTask(clientfd)
    |
 BlockingQueue
    |
 worker线程
    |
 task.Run()
    |
 recv/send

四、生产者消费者模型

生产者
accept线程：
accept客户端
生成TcpTask
Push任务

消费者
worker线程：

Pop任务
执行Run()

五、BlockingQueue

包含：
queue

mutex

condition variable

Push：
加锁
判断队列是否满
等待
插入任务
唤醒消费者

Pop：
加锁
判断队列为空
等待
获取任务
唤醒生产者

六、TcpTask

TcpTask保存：
clientfd
代表一次客户端连接。

Run：
Receive()
Send()
循环

任务结束：
close(clientfd)

七、Thread

Thread负责创建工作线程。

线程函数：
while(true)
{
    Pop(task);

    task.Run();
}
线程不会绑定某个客户端。
而是：
任务1结束
继续执行任务2
体现线程池复用。

十、遇到的问题

问题1：多个客户端抢占server输入
原因：
之前Send中使用cin。
多个worker同时：
Send()
 |
 cin
导致输入竞争。

解决：

改成请求响应模型：
client发送
server处理
server回复

问题2：线程池没有消费任务
错误：
线程一直处理固定任务。
正确：
worker
while(true)
Pop任务
Run任务

问题3：是否需要锁
需要锁的位置：
BlockingQueue。
原因：
多个线程同时访问任务队列。

不需要锁的位置：
TcpTask中的recv/send。
原因：
每个任务拥有独立clientfd。
