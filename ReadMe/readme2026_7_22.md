💎 Functions & Concepts & Core Snippets

1. Mutex

多个线程访问共享变量会产生数据竞争。

例如：

count++;

不是原子操作。

解决：

mutex.Lock();

count++;

mutex.Unlock();

Mutex保证临界区同一时间只有一个线程执行。

2. Deadlock

死锁产生：

线程1：

Lock(A)
等待B

线程2：

Lock(B)
等待A

形成循环等待。

解决：

固定锁顺序

减少锁数量

使用try_lock

3. Condition Variable

作用：

让线程等待条件，而不是不断循环检查。

错误：

while(queue.empty())
{
}

正确：

cond.Wait();

主要接口：

wait

signal

broadcast

4. Blocking Queue

结构：

Producer

 Push()

 BlockingQueue

 Pop()

Consumer

成员：

queue<Task> _qT;
Mutex _mutex;

Push:

加锁

判断是否满

满则等待

插入任务

唤醒消费者

解锁

Pop:

加锁

判断是否为空

空则等待

5. Producer Consumer

生产者：

queue.Push(task);

消费者：

Task task=queue.Pop();
task.Run();

实现任务和线程解耦。

6. Task抽象化

之前：

Task(int num)

只能执行固定任务。

修改：

Task(function<void()> func)

Task保存一个可执行函数。

例如：

Task t(
[](){
 cout<<"hello";
});

执行：

task.Run();

🐛 Mistakes & Debugging Loops

count结果错误

原因：

数据竞争。

解决：

Mutex保护共享变量。

Segment fault

原因：

线程对象生命周期或资源管理问题。

Condition无法唤醒

原因：

Signal时机错误。

正确顺序：

修改状态
Signal
Unlock

Task没有默认构造

原因：

只有：

Task(function<void()>)

没有：

Task()

增加默认构造即可。

❌ Ideological misunderstanding

Mutex不是提高速度

Mutex保证线程安全。

Condition不是锁

Mutex负责保护资源。

Condition负责等待和唤醒。

BlockingQueue不是ThreadPool

BlockingQueue：

存储任务。

ThreadPool：

管理线程并使用BlockingQueue。
